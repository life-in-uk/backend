# Replacement and frontend release safeguards

**Draft plan. Production publication stays on hold until the owner agrees the publication-consistency plan.** The hold covers existing-Guide replacements and the four new Money Guides in backend PR #90.

## Preserve translations and revisions

1. At implementation, retrieve the full current canonical source and all four locale revisions through the authorized owner path. Pin the current open publication UUID, source and locale revision IDs, canonical hashes, file hashes and validity window. Compare with [PUBLIC-BASELINE.json](PUBLIC-BASELINE.json). The public payload exposes source IDs and content hashes. It omits the stored publication UUID and individual locale revision IDs. For the GP Guide, the five API digests are captured but cannot be recomputed from the public projection with the ordinary DRAFT reconstruction; use the authorized canonical export before relying on a baseline for a replacement. The other 45 hashes recomputed.
2. Preserve the useful zh-CN/zh-TW prose and never edit a stored canonical revision. Use the same slug, category, jurisdiction, scope and core meaning across locales. For a changed Guide, create a genuine reviewed source revision with an honest date and retain the prior canonical files. Localize examples and summaries without changing shared UK rules. The existing gate requires the same ordered source references, evidence keys, support locators and source excerpts in every locale. Agree those against the revised Simplified Chinese source before translating. Keep localized evidence statements and notes accurate for each body. If an authentic locale-only change needs a source revision the existing flow refuses, stop for owner decision rather than churning timestamps or loosening a gate.
3. Produce five DRAFT files and a canonical manifest for each approved change. Run the Java Guide reader, quality gate, canonical hash comparison, numerical and date parity, link and source checks, RTL and metadata previews. Record which passages the locale reviewers checked and any limits. Keep the same public URLs and verify reciprocal hreflang. The China-specific records slug stays explicitly scoped unless a separate migration proposal is approved.
4. Rehearse a replacement against disposable PostgreSQL, using the approved source and translations. Confirm wrong or stale publication expectation fails closed, the five previous public locale variants remain in place until approval, and activation changes all five pointers together. Healthcare-adjacent content, clinical terms and banking protection still need review at the point of revision. No professional or native-speaker sign-off is implied by this plan.

## Protected production sequence after separate authorization

The new-slug manifest publisher must never be used for these replacements. Confirm an owner-authorized private operator and the existing draft, review and approval roles before scheduling. The current runbook does not offer a generic GitHub replacement dispatch. Follow the implemented loopback owner revision process and existing [replacement runbook](../catalogue-expansion-2026-11/REVISION-REVIEW.md#existing-owner-controlled-publication-path). Verify the appropriate checklist against the current implementation; the non-immigration replacements use the standard checklist if the gate confirms it.

- Take and verify the off-instance pre-change backup; store the last-known-good five-variant export privately. Create the DRAFT batch against the current `basedOnRevisionId` and use the existing translation exchange to bind all locale variants to that batch. Compare stage read-back revision IDs and hashes with the approved files.
- Record reviews against exact hashes through the approved review service and truthful provenance. After explicit owner approval and verified backup, publish with `expectCurrentPublicationId` set to the verified live UUID. Record the new and superseded publication IDs and all hashes. Confirm old canonical URLs still return 200, the API exposes the intended revisions, and unrelated Guides are unchanged.
- If rollback is required, use the previously retained reviewed content as a fresh owner-approved replacement against the now-current UUID. Verify hashes, five public pointers and rebuild the static site. Follow the documented emergency withdrawal path only if appropriate and authorized. A frontend rollback restores the previous artifact; it does not roll the API or backend sitemap back.

## SEO coordination and owner decision

Pair this plan with Claude's F4 sitemap source-of-truth review and F12 About work. The current backend sitemap follows public Guide records immediately. Static detail pages are built separately from a snapshot of the public API. A new Guide can therefore appear in the sitemap before its HTML exists, and a replacement can leave old HTML and metadata alongside new API content. Technical PR #50 addresses a different transient-render issue.

Before scheduling any publication, agree whether Claude's proposed frontend-owned sitemap will be ready or whether the owner accepts an explicitly coordinated fallback. The fallback uses both existing protected gates during the same window, pins the post-publication frontend artifact, verifies sitemap and frontend state after invalidation, and records the gap. Do not adopt a sitemap change in these editorial PRs. Follow the current approved architecture at release time.

For the replacements, verify the five variants, static contracts and Health hub copy for each changed slug. For the new Money Guides, verify 20 public detail URLs and updated category links. Confirm canonical, hreflang, rendered text, source links and Urdu RTL after deployment; treat the release as incomplete until API, sitemap and HTML agree. Any failed parity, stale pointer or missing approval stops release.
